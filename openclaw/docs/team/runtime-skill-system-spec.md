# Runtime Skill System Spec

## 1. 目标

定义 Project Runtime 的技能体系应该如何设计。

本规范回答三个问题：

- 哪些技能应当是所有 Runtime 的共性底座
- 哪些能力应当按项目差异化
- 如何让技能体系长期演进，而不是越积越乱

## 2. 基本判断

你的判断是对的：

- 不同 Runtime 面对的项目不同
- 但它们掌握的基础开发技能大体相同

差异通常不在“会不会开发”，而在：

- 维护的是哪个项目
- 管哪些 repo
- 用什么项目管理工具
- 遵循什么分支、测试、发布流程
- 有哪些项目特有的坑和经验

所以技能体系应当分层，而不是每个 Runtime 都从零长出一整套完全不同的技能。

## 3. 技能分层

建议将 Runtime 的技能体系分成两层：

### 3.1 基础工程技能层

这是所有 Runtime 共享的通用开发技能层。

默认建议使用：

- [mattpocock/skills](https://github.com/mattpocock/skills)

这层技能主要解决：

- 需求澄清
- 任务拆分
- 调试
- 测试
- 代码评审
- 文档更新
- 发布前检查

这层技能不应按项目重复造轮子。

### 3.2 项目补充技能层

这是某个项目自己的补充技能层。

这层技能主要描述：

- repo 结构
- 分支命名规则
- PR 合并规则
- 测试入口
- 发布流程
- 环境约束
- 常见故障模式
- 项目内部术语

这层技能应当随着项目长期演进。

## 4. 共性技能清单

所有 Runtime 原则上都应具备以下共性技能类别：

| 类别 | 作用 |
| --- | --- |
| 需求澄清技能 | 把模糊任务变成可执行任务 |
| 任务拆分技能 | 按 repo、模块、风险拆分工作 |
| 调试技能 | 排查失败、复现问题、定位根因 |
| 测试技能 | 确定应该跑什么测试、如何验证变更 |
| 代码评审技能 | 在提交前检查风险、回归和遗漏 |
| 文档同步技能 | 让代码变更同步沉淀到文档 |
| 发布检查技能 | 确认变更是否满足交付条件 |
| 项目管理工具协作技能 | 把任务沉淀到 issue / PR / project tool |

这些能力不应因项目不同而被重新定义。

## 5. 项目差异应该落在哪里

项目差异不应主要落在基础 skill 本身，而应落在以下几类内容：

| 差异类型 | 应落点 |
| --- | --- |
| repo 列表与职责 | `repo_map` |
| 项目管理工具配置 | `project_management_tool` |
| 代码规范 | 项目 skill 或项目文档 |
| 测试命令 | 项目 skill |
| 发布流程 | 项目 skill |
| 特有故障经验 | `MEMORY.md` 或项目 skill |
| 项目术语与边界 | `AGENTS.md` / `BOOTSTRAP.md` / 项目 skill |

这意味着：

- 基础工程 skill 负责“怎么做一类事”
- 项目 skill 负责“在这个项目里具体怎么做”

## 6. 技能设计原则

### 6.1 先复用，后定制

能用基础 skill 解决的，不要为单个项目重写一份新 skill。

### 6.2 项目 skill 只补充，不替代

项目 skill 应尽量补充项目上下文，而不是复制一遍通用工程流程。

### 6.3 一个 skill 只负责一个清晰职责

不要把“分析需求 + 修改代码 + 写 PR + 部署上线”塞进一个大 skill。

### 6.4 技能应绑定可验证输出

好的 skill 应该产出明确结果，例如：

- 一个 issue 拆分结果
- 一个复现路径
- 一个测试结论
- 一个 review 结果
- 一个发布检查清单

### 6.5 技能应可组合

Runtime 解决复杂任务时，应能把多个 skill 串起来，而不是依赖一个万能 skill。

## 7. 为什么不让每个 Runtime 自己长出完全不同的技能

如果每个 Runtime 都自由生长出一套完全不同的技能体系，会有几个问题：

- 团队行为不一致
- 同类任务质量波动大
- 新 Runtime 难以初始化
- 项目迁移成本高
- 很难复用已经验证过的工程方法

所以更合理的方式是：

- 共享一套基础工程技能底座
- 每个项目只维护自己的差异部分

## 8. 技能演进策略

技能演进建议遵循下面的顺序：

1. 先使用基础工程技能完成任务
2. 如果某类项目问题反复出现，再总结成项目 skill
3. 如果多个项目都需要同类 skill，再提升为共享基础 skill

判断是否应该新建项目 skill 的标准：

- 同类问题是否重复出现
- 是否需要固定输入输出
- 是否能明显降低以后执行成本
- 是否真的是项目特有，而不是通用工程问题

## 9. 第一阶段建议

第一阶段建议所有 Runtime 默认具备：

- `mattpocock/skills` 作为基础技能体系
- 项目级 `MEMORY.md`
- 项目级 `AGENTS.md`
- 项目级 `BOOTSTRAP.md`
- 项目自己的 `skills/`

第一阶段建议优先使用的基础技能包括：

- `/setup-matt-pocock-skills`
- `/grill-with-docs`
- `/triage`
- `/tdd`
- `/diagnose`
- `/requesting-code-review`
- `/document-release`

## 10. 结论

Project Runtime 之间最大的差异，不应是基础开发技能不同，而应是项目上下文不同。

所以合理的技能体系应当是：

- 共享基础工程技能
- 项目只补充自己的差异化技能
- 将重复经验逐步沉淀为 skill
- 保持 skill 小而清晰、可验证、可组合
