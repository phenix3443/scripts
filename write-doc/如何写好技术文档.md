# 如何写好技术文档

技术文档的核心职责：让读者（人或 AI agent）在不了解历史背景的情况下，读完就能知道**当前**系统是什么、为什么这样做、怎么验证。

---

## 原则一：只写当前事实

文档描述现在的状态，不记录演进过程。

**不写：**

- "一开始我们想……后来改成……"
- "之前遇到……所以现在……"
- "暂时先这样，后续再优化"

这些内容属于 Git commit、PR、ADR、changelog，不进主文档正文。

---

## 原则二：一个文档只回答一类问题

每份文档只承担一种职责。读者拿到文档前，应该能从文件名判断出"这里能找到什么答案"。

常见职责划分：为什么做（需求）、选什么方案（调研）、怎么设计（架构）、怎么实现（实现说明）、怎么验证（测试）、怎么运行（部署）。

---

## 原则三：结论优先，边界明确

好文档的信息顺序：定义 → 结论 → 理由 → 边界。

**不写：**
- 大段背景铺垫后才给结论
- "未来可能""后续考虑"写进当前方案正文
- 含糊词：暂时、目前先、之后再说、大概

用清单表达范围、非目标、验收标准——清单比段落更难遗漏边界。

---

## 原则四：对 AI agent 友好

文档会直接成为 agent 的上下文，额外要求：

- 每个概念只在一处定义，其他地方直接引用，不重复解释
- 关键术语首次出现时给出精确定义（一句话）
- 命令、路径、配置键名用 `` `代码块` `` 标注
- 避免代词指代不明（"它""这个"），直接写名词

---

## 什么时候更新文档

**触发标准：** 有人按现有文档操作，会得到错误结果。

过程性事件（临时问题、一次性调试、某次失败）不触发文档更新——那些属于 issue 或 runbook。

---

## 提交前自查

- [ ] 无历史演进叙述
- [ ] 每份文档只承担一种职责
- [ ] 无模糊时间词：暂时、之后、目前先、后续可能
- [ ] 结论先于理由，定义先于边界
- [ ] 命令、路径、配置键名使用代码块标注
- [ ] 与代码 / 配置的实际状态一致
